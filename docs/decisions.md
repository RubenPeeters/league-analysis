# Decisions

## 2026-11-15: managed by forge

The repo is managed by forge: one issue, one branch, one PR into `dev`; `main` is released code.
`make check` (ruff and pytest through uv) is the gate, locally and in CI.
**Why:** the site had been publishing an empty `data.json` since 2026-10-21 without anyone noticing; Ruben asked to add the repo to forge before fixing and improving it.

## 2026-11-15: data.json lives on the `data` branch

`update_data.yml` commits each generated `data.json` to the `data` branch and no longer to `main`. `data/` is not tracked on `main` or `dev`. The history up to this date remains in the history of `main` (commits "Auto-update data").
**Why:** forge protects `main` against direct pushes, so the 6-hourly commit to `main` could not continue. A separate branch keeps the snapshot history, which is the only archive: MongoDB is purged at every patch.

## 2026-11-15: src/main.py left unchanged at adoption

The adoption commit did not touch `src/main.py`; it is excluded from ruff in `pyproject.toml` until it is restructured.
**Why:** the script runs its database and API calls at import, so it could not be tested; changing it without tests was left to its own issue.

## 2026-11-15: src/main.py restructured, still one file

`src/main.py` does nothing at import; `main()` builds the clients, the collection and the Data Dragon data and passes them down. The crawler (`crawl`) is separate from the analysis (`build_frontend_data` and its helpers), which is pure. It stays one file at the same path, and is linted.
**Why:** to make it testable (#2) without touching `update_data.yml`, which calls `python src/main.py` and which the forge bot cannot change. Tests import it through `pythonpath = ["src"]` in `pyproject.toml`.

## 2026-11-15: a failed Riot run writes nothing and purges nothing

`main()` exits 1 without purging the database or writing `data.json` when the Riot API rejects the key (401/403) or when no region could be scanned. The purge of old-patch matches now runs after the crawl instead of before it.
**Why:** a rejected key produced a green run that published an empty `data.json` every 6 hours (#3). A non-zero exit stops `update_data.yml` before its commit and deploy, so the site keeps its last good data; purging only after the API has answered means a broken key cannot empty the database.

## 2026-11-15: both sides counted; pick_rate is per role slot

`aggregate()` counts both players of the role in every match, for champion statistics, builds, context builds and leaderboards. `pick_rate` is picks of the champion in the role divided by the number of role slots (2 per match), as a percentage. `ban_rate` is unchanged: bans divided by matches.
**Why:** only the blue-side player of each role was counted, so half the picks were ignored (#10). Dividing by role slots instead of matches keeps a role's pick rates summing to about 100, the scale the site and the per-patch archive on the `data` branch already use.

## 2026-11-15: per-patch archive in history.json on the `data` branch

The meta of each patch is kept in `history.json` on the `data` branch, one entry per patch. `update_data.yml` copies it into `data/` before the generator runs and commits it back afterwards; the site publishes it with `data.json`. The entries for 16.2 to 16.20 were backfilled by `analysis/meta_over_patches.py` from the `data.json` versions in the history of `main`; they are marked `"source": "backfill"` and hold only the 15 most-picked champions per role, blue side only, with estimated game counts.
**Why:** Ruben asked for a page on the site showing how the meta changed over the patches. MongoDB is purged at every patch, so the per-patch result has to be stored when it is produced; a file on the `data` branch keeps it in git next to the snapshots and keeps the generator free of extra database state.

## 2026-11-15: meta over patches page reads history.json as is

`ui/history.html` shows `history.json` as a grid of pick rates per champion and patch. Its rows are every champion that was in the top 15 by pick rate in at least one patch. They are ordered by the number of patches in the top 15, then by the mean pick rate over the patches where the champion is listed. A champion that is not listed shows as an empty cell. The logic lives in `buildView` in `ui/history.js`, which `tests/test_history_page.py` runs through node (skipped if node is missing).
**Why:** backfilled patches only list the top 15, so a missing entry is unknown, not 0, and counting it as 0 would distort both the colours and the order (#12). Testing the JavaScript through node keeps `make check` as the only gate without adding a JS toolchain.

## 2026-11-15: finished items chosen by shop data, not recipe depth

`select_items()` picks build items from the parsed Data Dragon `item.json`. A finished item is on Summoner's Rift (`maps["11"]`), is not a consumable or trinket, has no `into`, and is either purchasable for at least 1000 gold or reached without a purchase: it has a `specialRecipe` (Muramana, Seraph's Embrace, Fimbulwinter) or is built only from items that cannot be bought (the support upgrades from Bounty of Worlds), and is not itself the `specialRecipe` of another item. Boots are a separate set: items tagged `Boots` that are built from something (tier 1 excluded), whatever their `into`. Builds count items from both sets, as before. When Data Dragon cannot be reached there is still no filtering.
**Why:** the old `depth >= 3` rule dropped Infinity Edge and Rabadon's Deathcap, which have depth 2 in 16.22.1 (#20). 1000 gold lies between the dearest starting item (Guardian's items, 950) and the cheapest finished non-boot item (Mejai's Soulstealer, 1500) in 16.22.1. Transformed items count because they are what the end-of-game inventory shows.

## 2026-11-15: item frequencies replace the exact set

Per champion, `data.json` has `items` (finished items other than boots) and `boots` in place of `top_items`. Each lists the item id, the number of games the item was in the final inventory (counted once per game) and that number as a percentage of the champion's games (`count`), at most 8, by share. Every game counts in the denominator, also games with few or no finished items. The detail view shows the share under each item and the game count on hover or tap, with item names from Data Dragon. `context_builds` is unchanged for now.
**Why:** the inventory slot order is not purchase order, so "the first three items" was arbitrary, and an exact set fragments at about 35 games per champion: on 2026-11-15, 44 of the 150 champion rows showed only two items and 98 had boots as one of the three (#21).

## 2026-11-15: matchup cards show item differences, enemy type from champions

The enemy type of a game comes from the enemy champions, not from the damage they dealt in that game. Each champion's physical share is its physical damage to champions divided by its total damage to champions (physical, magic and true), summed over all its stored games in any role and both regions; the magic share likewise. A champion with fewer than 5 stored games has no share and is left out of the team mean. A team is Heavy AD when the mean physical share of its champions is above 65%, otherwise Heavy AP when the mean magic share is above 60%, and Tank Heavy (also) with two or more champions tagged `Tank` in Data Dragon. `matchups` replaces `context_builds` in `data.json`: per enemy type, the items (boots included) whose share in games against that type differs from their share in the champion's other games (same role and region) by at least 20 percentage points, with both shares and both game counts, ordered by the difference. A card needs at least 10 games against the type and 10 other games, and at least one item.
**Why:** on 2026-11-15, 218 of the 313 published cards rested on fewer than 10 games and 103 showed the same build as the default, and the damage dealt describes how the game went, not what the player faced in champion select (#22). A difference against the champion's own other games shows only what changes; 10 games per side keeps one game from moving a share by more than 10 points.

## 2026-11-15: runes, summoner spells and game length stored; older matches downloaded again

`slim_match()` also keeps, per participant, the rune page as `perks` (`primaryStyle`, the four `primary` selections, `subStyle`, the two `secondary` selections and the three stat `shards` in the order offense, flex, defense; `None` when the response has no perks), `summoner1Id`, `summoner2Id` and `gameEndedInEarlySurrender`, and per match `gameDuration`. `gameDuration` is always written, also as `None`, so its presence marks a match slimmed with these fields. After the crawl, every stored current-patch match without it is downloaded again through `smart_request` and replaced, one request per match; a match that cannot be fetched is left as it is and tried again only in a later run. `data.json` is unchanged; the analysis does not read the new fields yet.
**Why:** runes, summoner spells and remakes need these fields, and the 1,065 matches stored on 2026-11-15 do not have them (#23). Downloading them again costs one request per match, once; without it, those views would stay partly empty until the next patch purges the old matches.

## 2026-11-15: runes and summoner spells per champion; remakes left out of builds

Per champion, `data.json` has `rune_games` (games with rune data), `runes` and `spells`. A rune page is the keystone, the primary style and the secondary style; `runes` lists the 3 most frequent pages with games, share of `rune_games` and win rate, and the first page has `selection`: its most frequent full selection (the other three primary runes, the two secondary runes, the three shards) with its game count. `spells` lists the 2 most frequent summoner spell pairs, order ignored, with games and share of `rune_games`. Games that ended in an early surrender (remakes) are left out of items, matchup cards, runes and spells, but still count for pick rate, win rate and KDA; item shares are now over `item_games`, the champion's games that are not remakes. The detail view shows runes and spells with names and icons from Data Dragon; stat shard names are fixed in `ui/script.js` because `runesReforged.json` does not list them.
**Why:** Ruben asked for runes and spells per champion (#24). The minor runes and shards vary much more than the keystone and the two trees, so a page defined by all of them fragments the sample the way exact item sets did (#21); the full selection is shown only for the top page. A remake ends before anything is bought or played out, so it would only dilute the shares. Matches stored before #23 have no rune data, so shares are over the games that have it, and the page shows that number.

## 2026-11-15: matches of previous patches kept within a window; each match downloaded once

The match list is requested for ranked solo queue only (`queue=420`), and `slim_match()` keeps `queueId`. Each list is scanned newest first. A listed match that is not stored is downloaded and stored when its patch is inside the retention window: the current patch and the `KEEP_PREVIOUS_PATCHES` patches before it (default 2), taken from the Data Dragon version list. The first match older than the window is recorded by id in the `old_match_ids` collection, with the current patch as `seen`, and ends the scan of that list; a recorded id met again also ends the scan and updates `seen`. Every run deletes stored matches older than the window and stored matches whose `queueId` is not 420; stored matches inside the window without `queueId` or `gameDuration` are downloaded again first, so legacy flex or normal games are then deleted. Id records are never deleted: a player who leaves the scanned ladder can return patches later with the same list, and Riot documents no limit on how far back a list reaches; `seen` only tells the last patch a list returned the id. `data.json` and the current patch's `history.json` entry read current-patch matches only. Per region the run logs matches listed, already stored, downloaded and recorded as too old, and it logs the storage size of the matches collection.
**Why:** older-patch matches were discarded after downloading and so downloaded again every run; on 2026-11-15 a run took 98 minutes and saved 4 matches (#33). Now each match is downloaded once, older games stay available for the per-patch archive and for player analysis, and the window bounds storage on the 512 MB Atlas free tier.

## 2026-11-15: regions crawled at the same time

`crawl()` scans each region in `REGIONS` in its own thread (standard library `threading`); within a region requests stay sequential and `smart_request` still waits out `Retry-After` on a 429. The threads are joined before anything else runs. A `RiotAuthError` in any region is raised after both threads finish and stops the run with exit 1, before the purge and before `data.json` is written; any other region failure is logged and the other region's result is kept, as before. Log lines carry the thread name, which is the region code (`kr`, `euw1`; `MainThread` outside the crawl). `smart_request` counts every attempt, 429 retries included, per thread, and a successful run's log ends with each region's Riot request count and crawl duration. Both threads share one `LolWatcher` and its `requests.Session`.
**Why:** Riot applies the application rate limit per routing host: on 2026-11-15 the headers showed `europe` at 100 of 100 requests in the 120-second window while `euw1` was at 1, so KR (`asia`) and EUW (`europe`) never compete for one limit, and scanning them one after the other left half of it unused (#34). Threads need no new dependency, and the crawl spends its time waiting on the network, where the GIL does not matter.

## 2026-11-15: match timelines stored slim

For each newly stored match the crawler also requests the match-v5 timeline through `smart_request` and stores `slim_timeline()` of it as the match document's `timeline`: per participant `puuid` (timeline participants are matched by `puuid`, not by position), `items`, the `ITEM_PURCHASED` (`buy`) and `ITEM_SOLD` (`sell`) events of finished items and boots with their timestamp, an `ITEM_UNDO` removing the last purchase or sale it reverts; and `skills`, the `SKILL_LEVEL_UP` events with `levelUpType` `NORMAL` (evolves left out) with timestamp and skill slot. When Data Dragon cannot be reached every item is kept, as builds then do. A match whose timeline request fails is stored without `timeline`; after the crawl, every stored current-patch match without the field gets its timeline requested again. A timeline Riot reports as not found is stored as `timeline: None` and not asked for again. A rejected key still stops the run. The log states per region how many timelines were fetched with the matches, and after the crawl how many were fetched for stored matches and how many current-patch matches are still without one. `data.json` is unchanged.
**Why:** the timeline is the only source for the order in which items are bought and abilities are levelled (#25). The raw timeline is far larger than the match and the database is on the 512 MB Atlas free tier, so only these events are kept. The cost is one more request per match, so downloading new matches takes roughly twice as long; matches already stored on the current patch cost one request each, once.

## 2026-11-15: build order and skill order per champion from the timeline

Each champion (per role and region) gets `timeline_games`, `first_items`, `paths`, `boots_position`, `skill_start` and `skill_max` in `data.json`, next to the item frequencies, which stay. Only games that are not remakes and have a stored timeline count; `timeline_games` is their number.
- A game's item order is its finished non-boot items in order of first purchase. Sales are ignored, so an item sold later counts at its purchase position; buying it again does not add it twice.
- `first_items`: every first item, most frequent first, share over `timeline_games`, with games and win rate. A game with no finished item counts in `timeline_games` only.
- `paths`: the 3 most frequent ordered first three items, with games. Games with fewer than three finished items are left out.
- `boots_position`: for the boots that are most often a game's first boots, in how many games, and the median number of finished items bought before them.
- `skill_start`: the most frequent order of the first three level-ups. `skill_max`: the most frequent order in which Q, W and E reach rank 5; when only two reach it, the third is put last; a game where fewer than two reach it is left out.
**Why:** the issue (#26) asked for the order players build and level in, which the final inventory cannot show. The timeline stored by #25 has the purchase and level-up times; counting from the first purchase keeps the order that of the build path, not of what was left at the end.

## 2026-11-15: one player's ranked matches share the ladder's store and retention window

`src/player.py` has `download_player_matches()`, and `python src/player.py "name#tag" kr|euw1` runs it for one player. It resolves the Riot ID with account-v1 on the region's routing host (`asia` for `kr`, `europe` for `euw1`), lists up to `PLAYER_MATCH_COUNT` (default 100) ranked solo matches (`queue=420`, in pages of 100), and scans the list with `scan_match_list()`, the same function the ladder crawl now uses per player: same `smart_request` path, same `matches` collection and document shape, same retention window, same stop at the first match older than the window (recorded in `old_match_ids`), and a match already stored is not downloaded again. It reports progress as (matches done, matches total) and returns the `puuid` and the ids of the player's matches inside the window. An unknown Riot ID raises `UnknownRiotIdError`; a rejected key raises `RiotAuthError`. The slim timeline also keeps `start` per participant: the ids of every item bought in the first 60 seconds, any item, with undo applied. Matches stored without `start` are kept as they are; nothing reads it yet. The scheduled run is unchanged, except that the purge also removes player matches once they leave the window, and that stored player matches of the current patch count in `data.json` like ladder matches, since nothing marks where a match came from.
**Why:** player analysis needs the same fields as the meta views, and a top player's matches are often already stored by the ladder crawl, so one store avoids downloading them twice and lets the player be compared with the ladder on the same patches (#35). The window keeps the 512 MB Atlas free tier bounded no matter how many players are looked up. Starting items are cheaper than finished ones and so are filtered out of `items`; the first minute covers the fountain purchases.

## 2026-11-15: player analysis per champion and lane opponent

`analyze_player()` in `src/player.py` takes stored matches, a `puuid` and the stored matches of the current patch (the ones `data.json` is built from), and returns a JSON-serialisable result; nothing calls it yet. Remakes are left out entirely, also from games and win rate. Per champion, role and region with at least 5 of the player's games (`PLAYER_MIN_GAMES`) it runs the player's games through `aggregate()`, so items, boots, rune pages, spells, item order and skill order are the ladder's statistics computed the same way, and adds `starting_items`: the 3 most frequent sorted lists of items bought in the first 60 seconds, over `start_games` (games whose timeline has `start`). Each item, boots, rune page and first item gets `ladder_share` from an uncapped `aggregate()` (`capped=False`: every item and rune page, not the 8 and 3 that `data.json` shows) of the same champion, role and region; it is `0.0` when the ladder never has the row, `None` when the ladder does not have the champion or no games of that kind (no rune data, no timeline), and `ladder` gives the ladder's game counts or `None`. The lane opponent is the enemy with the same `teamPosition`; a game without one counts only for the champion. An opponent needs at least 3 games (`OPPONENT_MIN_GAMES`); its item differences are `aggregate()`'s matchup cards with the opponent as context, at least 20 points apart, which also need 1 of the champion's other games and are empty otherwise.
**Why:** the comparison with the tracked top players is the point of the page (#36), so the player's numbers must come from the same functions as the ladder's. A player has far fewer games than the ladder: 5 games on a champion is the smallest sample where one game moves a share by at most 20 points, and 3 games against one opponent is lower because a player meets one opponent far less often than they play one champion, while a single game still cannot decide the row. The item differences ask only 1 other game, because with the opponent at 3 the rest of a 5-game champion is often 2 games, and requiring 3 there hid real differences. The ladder's own 10-game matchup minimum is unchanged. `data.json` only carries the top rows, so the ladder shares come from the matches themselves, so that every player row has a comparison.

## 2026-11-15: the player lookup runs as a service on the Hetzner box, behind a Discord server role

`src/web.py` is a FastAPI application (run by uvicorn, pages rendered with Jinja2 using `ui/style.css`), packaged with a `Dockerfile` and a `compose.yaml` that publish it on `127.0.0.1:8000` for the box's Caddy to proxy. Login is Discord's OAuth2 authorisation code flow with scopes `identify` and `guilds.members.read`; the `state` is kept in a signed, 10-minute cookie and compared on the callback. The callback reads the user's member object for `DISCORD_GUILD_ID` and lets the user in only when its roles include `DISCORD_ROLE_ID`; anyone else sees that access is by invitation. The Discord access token is used only within the callback request and never stored. The session is a signed cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, itsdangerous) holding the Discord user id and name, valid 24 hours from login and never extended, so a removed role stops working within a day. All configuration comes from the environment and the service refuses to start when any of it is missing. The GitHub Pages site is unchanged; `/` is a placeholder until the lookup page exists.
**Why:** a static page cannot hold the Riot key or run a download, so the lookup needs a server, and the Hetzner box already runs Caddy (#37). Every lookup spends the shared Riot rate limit of 100 requests per 2 minutes, the same one the scheduled crawl uses, so the lookup cannot be public: access is by invitation, and a role on the Discord server where the invited players already are is the cheapest way to grant and revoke it. Starlette's own session middleware was not used because it re-signs the cookie on every response, which would keep an active user's session alive past a removed role.

## 2026-11-15: player lookups are queued jobs, reused for 6 hours, 10 per user per day

`/` has a form for a Riot ID and region (KR or EUW) and lists the user's last 10 lookups. The Riot ID is checked before anything is stored or requested: a game name of 3 to 16 characters without `#`, `/`, `\`, `?`, `%` or `&`, then `#`, then a tag of 3 to 5 letters or digits. A lookup is a document in `lookup_jobs` (Riot ID as typed and case-folded, region, requesting Discord user id, state, progress, reason, result, created, started and finished times). One worker thread in the service claims the oldest queued job, marks it running, and runs `download_player_matches()` and `analyze_player()` against the stored current-patch matches of the same region; the result, with Data Dragon names for the page, is stored on the job. States are `queued`, `running` (with matches done and total), `done` and `failed` with reason `unknown_riot_id`, `riot_key_rejected` or `other`. Jobs left `running` are put back in the queue when the service starts. A database error in the worker is logged and the worker retries after 5 seconds, first putting a job left `running` back in the queue. The comparison baseline is every stored current-patch match of the region, the same matches `data.json` is built from, so it includes matches stored by earlier lookups (see the #35 entry: nothing marks where a match came from). The job page reloads itself every 5 seconds until the job ends. A request for a player and region that is queued, running, or done within `LOOKUP_REUSE_HOURS` (default 6) opens that job and adds it to the user's recent lookups; a later request is a new job, which downloads only matches not stored yet. A user can start `LOOKUPS_PER_DAY` (default 10) new jobs per rolling 24 hours; reused jobs do not count.
**Why:** the issue asked for it (#38). Every lookup spends the shared Riot rate limit of 100 requests per 2 minutes that the scheduled crawl also uses, and a 100-match lookup costs about 200 requests the first time, so jobs run one at a time and per-user volume is capped. The scheduled run refreshes the ladder every 6 hours, so a result younger than that compares against nearly the same ladder and a new download would mostly find nothing new. 10 a day lets a member look up a team and its opponents without one person using the limit for everyone. A rolling 24 hours needs no time zone. The queue lives in MongoDB, already used for matches, so a restart loses no request.

## 2026-11-15: champion view is compact, with the detail in tooltips

The champion view shows a header strip (champion, role, region, patch and five statistics) and one screen of small panels (runes, build path, final items and boots, spells and skills, changes by enemy team) built from icons, bars and percentages; names, descriptions, exact counts and how each number is counted are in a tooltip on hover or focus (so a tap works on a phone), kept inside the viewport and closed by Escape. Anything under 10 games, including a player row, is dimmed, loses its win-rate colour and says so in its tooltip. The players table shows 8 rows until asked for all. Text from Riot and Data Dragon is escaped before it goes into the page.
**Why:** the earlier view listed every statistic as a sentence, which took several screens and hid the comparison between rows. The layout follows what other stats sites do (u.gg, op.gg, lolalytics).

## 2026-11-15: `make screenshots` for visual review

`scripts/screenshots.py` photographs the home page, the champion view (with and without a tooltip) and the history page at 375px and 1280px, from a fixture in `tests/fixtures/site/` (a cut-down copy of the data published that day, player names replaced by placeholders). `.forge.toml` sets `screenshots = "make screenshots"`. Playwright is a dev dependency; the script runs it on the `node` found on PATH when there is one, because Playwright's bundled node needs `libatomic`, which the forge runner image lacks. The champion shots open Jarvan IV, the fixture's KR jungler with a "changes by enemy team" card, so every panel is in the picture.
**Why:** forge's reviewers can only judge a layout from pictures, and a fixed fixture keeps the pictures unchanged unless a page changes.
